The crew

A lead, and a specialist per lane.

Fourteen specialists, each in its own lane, and one lead that writes no production code.

The lead plans, delegates, commits.

It writes a plan with acceptance criteria, waits for your go-ahead, dispatches each step to a specialist, and commits the step once it passes. It is the only agent that touches git.

Plan

  • analystAcceptance criteria, content needs, a tracking plan.
  • architectContent models, Graph schemas, catalogs, integrations.
  • designerThe tokens and component specs the frontend builds to.

Build

  • backendServer code, with the Optimizely skill for your version.
  • frontendViews and components, Razor included.
  • copywriterUI and editor copy, resource and locale files.
  • generalistSmall, low-risk changes across lanes.

Test and review

  • unit-testsBackend tests, plus component tests when configured.
  • e2eBrowser tests with Playwright or Cypress.
  • visual-reviewThe build against the design, by token.
  • security-reviewThe security part of the review gate.
  • web-reviewSEO, accessibility and performance.

After merge

  • incident-triageA production signal to the code and the suspect commits.
  • debt-scoutReady-to-paste debt pointers for a scope you name.

Commands

Or open a claude --agent crew:lead session and just describe the work.

  • /crew:initOnce per project: record the stack, the build, test and lint commands, and the formatters.
  • /crew:featurePlan, delegate, build, and stop at the review gate.
  • /crew:reviewGO or NO-GO: code, security and design review, plus build, test and lint.
  • /crew:prPush the branch and open the pull request. The only way out of the machine.
  • /crew:addressRoute review comments and CI failures back to the crew, then run the gate again.
  • /crew:debtFix one debt pointer: a suppression, an analyzer rule, a package upgrade. Beta
  • /crew:triageA bug report, trace or alert → the code and the suspect commits.
  • /crew:loopRun the lead again each tick until the plan's exit conditions are met.
Guardrails

Hooks, not promises.

A prompt is a suggestion to a model. These run in the harness before each tool call, so a worker cannot talk its way past them.

  • One pair of hands on git. Only the lead runs git, on a feature branch.
  • Writes stay in lane. Shell writes that would route around the guard are refused.
  • Destructive commands refused. Force-push and writes into .git/ are blocked.
  • Nothing leaves on its own. No push and no pull request until you run /crew:pr.
# backend tries to commit
$ git commit -m wip
Blocked: backend runs no git but a plain `git mv`. Return your result; lead commits verified steps.

# frontend edits through the shell
$ sed -i s/a/b/ src/app.ts
Blocked: sed writes a file from Bash, which reaches no Edit|Write hook. Use Edit/Write.

# a worker starts a dev server
$ npm run dev
Blocked: watch/dev/serve commands never terminate. Use the one-shot build/test command.
